# Sprint Planning — TiendaAdmin POS

## Description

This directory contains the sprint planning documentation for the TiendaAdmin Point of Sale (POS) project.

## Sprint 1 — Planning and Documentation

### Sprint Goal

Establish the initial project documentation, system requirements, database design, user stories, security requirements, and GitHub collaboration workflow before starting software implementation.

## Sprint Scope

Sprint 1 focuses on documentation and project organization.

No application source code will be delivered during this sprint.

## Sprint Deliverables

1. Functional and non-functional requirements.
2. Use case descriptions and diagrams.
3. Entity-Relationship (ER) model.
4. User stories and acceptance criteria.
5. Security requirements.
6. GitHub repository documentation structure.
7. Gitflow branching strategy.
8. GitHub Projects board and assigned Issues.
9. Commits and Pull Requests demonstrating team collaboration.

## Team Responsibilities

The project consists of four team members.

| Team Member | Proposed Responsibility |
|---|---|
| Team Member 1 | Functional and non-functional requirements |
| Team Member 2 | Use cases and user stories |
| Team Member 3 | Entity-Relationship model and data dictionary |
| Team Member 4 | Security requirements and Gitflow documentation |

These assignments are preliminary and must be confirmed by the team.

All team members will participate in documentation review and validation.

## Sprint Workflow

The team will use GitHub Projects to organize and track tasks.

Each task must include:

- A descriptive title.
- A clear description.
- An assigned team member.
- Acceptance criteria.
- A priority.
- A status.

## Gitflow Strategy

The repository will follow these branching conventions:

- `main`: Stable and approved documentation.
- `develop`: Integration branch.
- `feature/*`: Individual documentation tasks.
- `release/*`: Release preparation when required.
- `hotfix/*`: Urgent corrections when required.

Changes will be integrated through Pull Requests.

Definition of Done

A Sprint 1 task will be considered complete when:

- The required documentation has been created.
- Its content is consistent with the project requirements.
- Acceptance criteria have been satisfied.
- The assigned team member has completed the work.
- The documentation has been reviewed.
- Changes have been integrated through a Pull Request.
- The corresponding GitHub Issue has been updated.
